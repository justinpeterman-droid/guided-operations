# Domain Glossary

Use these terms consistently in UI copy, schema names, API contracts, tests, and
documentation. A new synonym should be introduced only when it describes a
genuinely different concept.

| Term                             | Canonical meaning                                                                                                               | Important distinction                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Guided Operations**            | The web product described by this repository.                                                                                   | Not the legacy Flask site, desktop companion, or Google Cloud deployment.                                  |
| **Facility**                     | The one configured operational organization served by the initial product.                                                      | There is no facility selector or multi-tenant administration in the first release.                         |
| **Employee number**              | The normalized user-facing login identifier assigned to a staff member.                                                         | It is not a password, public ID, database authorization rule, or proof of identity.                        |
| **PIN-like credential**          | The user's secret used with employee number at sign-in.                                                                         | Never call a temporary credential the user's existing PIN; plaintext is never stored or displayed.         |
| **Authentication identity**      | The verified session principal, typically tied to a Supabase Auth subject or server identity adapter.                           | Separate from staff profile and incident role.                                                             |
| **Web account**                  | Authentication/authorization state: employee-number mapping, role, active state, credential lifecycle, and sessions.            | Separate from descriptive employment information.                                                          |
| **Staff profile**                | Approved directory attributes used for display and attribution.                                                                 | Deactivation must not erase historical records.                                                            |
| **Officer**                      | The standard interactive application role.                                                                                      | Rank or supervisor title does not automatically change this permission role.                               |
| **Administrator**                | The elevated interactive role for facility-wide oversight and account administration.                                           | Not a deployment operator, database owner, corpus manager, or service principal.                           |
| **Step-up authentication**       | A fresh verification required before a sensitive administrator or account action.                                               | Different from simply having an active session.                                                            |
| **Incident**                     | The canonical digital folder that connects facts, people, reports, paperwork, actions, and history under one incident identity. | Not a generated report or a copy in another records system.                                                |
| **Incident number**              | The official or product-assigned human-readable identifier for an incident.                                                     | Use an opaque internal key for URLs and joins; do not rely on the display number as the sole database key. |
| **Reporting officer**            | The employee whose first-person report is represented.                                                                          | May differ from the employee entering/preparing the report.                                                |
| **Preparing officer**            | The employee who creates or edits material on behalf of a reporting officer.                                                    | Preparation does not transfer authorship or create a separate incident copy.                               |
| **Involved officer**             | An employee connected to the event.                                                                                             | Being involved does not automatically grant edit permission.                                               |
| **Field notes**                  | Employee-entered source notes in the employee's own words.                                                                      | Not confirmed structured facts and not a final narrative.                                                  |
| **Proposed fact**                | A candidate structured value extracted from notes or entered before confirmation.                                               | Must not populate official output as if confirmed.                                                         |
| **Confirmed fact**               | A structured value explicitly reviewed and accepted by an authorized employee in a specific revision.                           | Confirmation is revision-specific and attributable.                                                        |
| **Missing-information question** | A targeted prompt for information required by an approved workflow or form.                                                     | A missing answer stays missing; the system does not guess.                                                 |
| **Gap answer**                   | The employee's response to a missing-information question, including explicit Unknown or Not applicable.                        | It is not automatically a confirmed fact until the workflow records it as such.                            |
| **Incident category**            | An approved classification that drives workflow and form rules.                                                                 | Descriptive labels and official disciplinary charges are separate concepts.                                |
| **Workflow progress**            | A calculated officer-facing summary derived from durable completion facts.                                                      | Not an arbitrary officer-controlled status.                                                                |
| **Record state**                 | Administrator-controlled lifecycle such as open, closed, reopened, transferred, or archived.                                    | Separate from workflow progress and always audited.                                                        |
| **Report**                       | A revisioned narrative or copy-oriented text output connected to an incident and reporting officer.                             | It is not the incident itself.                                                                             |
| **Officer report**               | Editable, attributable report intended for supported print/download when permitted.                                             | Different from copy-only records-system text.                                                              |
| **Copy to Records**              | Clean plain text deliberately copied for entry into an external records system.                                                 | Never presented as a printable official substitute.                                                        |
| **Supervisor Summary**           | A copy-only report type for supervisor/records use.                                                                             | No Print or Download Word action unless an approved requirement changes.                                   |
| **Disciplinary Supplement**      | A copy-only report type for disciplinary/records use.                                                                           | No Print or Download Word action unless an approved requirement changes.                                   |
| **Packet**                       | The ordered collection of reports, digital forms, checklists, reminders, and physical-only tasks for an incident.               | A packet can be incomplete and must expose why.                                                            |
| **Packet item**                  | One versioned entry in an incident packet, with source, capability, completeness, and action metadata.                          | It may represent a digital document or a physical-only task.                                               |
| **Required paperwork**           | Packet items selected by approved deterministic rules from confirmed facts.                                                     | “Required” must have a rule and source; AI suggestion alone is insufficient.                               |
| **Suggested paperwork**          | Approved items recommended by deterministic rules or a reviewable suggestion process.                                           | User may add/remove where policy allows.                                                                   |
| **Additional form**              | An approved item manually added from Forms Library.                                                                             | Must not bypass source/version/rights checks.                                                              |
| **Physical-only form**           | An official paper/carbon-copy process the app may guide but must not digitally replace.                                         | The app may show confirmed handwriting guidance and record acknowledgment only.                            |
| **Form definition**              | Versioned metadata describing an approved form's source, fields, capabilities, and validation rules.                            | Not necessarily the source document bytes.                                                                 |
| **Form preview**                 | A screen representation of a form populated from confirmed facts.                                                               | It is not accepted merely because a generic key/value preview exists.                                      |
| **Document action**              | A deliberate preview, print, download, copy, or physical-completion acknowledgment.                                             | Logging an action does not prove an external filing occurred.                                              |
| **NCU Days Count**               | The browser-fillable, printable count sheet workflow based on the approved NCU source structure.                                | Mismatches remain visible and are never auto-corrected.                                                    |
| **Daily Paperwork**              | Revisioned routine records used each day, such as roster and inspection/check logs.                                             | Separate from incident packets.                                                                            |
| **Weekly Paperwork**             | The weekly routine-paperwork category.                                                                                          | The canonical old source contains an empty weekly catalog; no template is implied.                         |
| **Monthly Paperwork**            | The monthly print set defined by approved monthly templates.                                                                    | Source implementation is primarily print-oriented and needs parity review.                                 |
| **Revision**                     | An immutable historical version plus the current canonical pointer/state.                                                       | Editing creates a new revision or controlled successor; it does not erase history.                         |
| **Base revision**                | The version a client read before attempting a write.                                                                            | A stale base revision causes a conflict rather than silent overwrite.                                      |
| **Conflict**                     | A rejected stale write because the canonical record changed.                                                                    | The UI preserves visible local content and guides recovery; it must not claim success.                     |
| **Idempotency key**              | A unique request token that makes a retried mutation produce one logical effect.                                                | It does not replace revision/concurrency checks.                                                           |
| **Audit event**                  | Redacted metadata stating who performed which bounded action, when, and against which record/revision.                          | Not a narrative dump, policy-query log, or storage location for secrets.                                   |
| **Fictional data**               | Clearly invented, non-identifying operational/personnel content used for development and validation.                            | Real names with altered numbers are not safely fictional.                                                  |
| **Policy source**                | One authorized, versioned source document in the RAG corpus.                                                                    | Its existence in an old filename manifest does not prove the bytes or rights are available.                |
| **Policy ID**                    | Opaque stable identifier assigned by the new corpus registry.                                                                   | Never expose raw filesystem paths or object-storage keys as IDs.                                           |
| **Policy page**                  | Extracted text and mapping for one source page.                                                                                 | Page number means the visible/document page convention recorded for that source.                           |
| **Policy chunk**                 | A bounded passage derived from one or more mapped source pages for retrieval.                                                   | It must retain source, page span, order, extraction version, and text hash.                                |
| **Citation**                     | A verified reference from an answer claim to an authorized source passage and page mapping.                                     | A source title alone, lexical guess, or model-created page number is not sufficient.                       |
| **Policy Expert**                | The question-answer workflow that returns cited guidance from authorized policy sources.                                        | It is guidance, not a legal opinion, final operational decision, or substitute for current policy review.  |
| **Full Policy Reader**           | The authorized source-viewing experience opened from a citation or policy catalog using an opaque policy ID.                    | Old implementation is branch-only and Flask-specific; it has not been ported.                              |
| **RAG**                          | Retrieval-augmented generation: retrieve authorized passages, generate within that evidence, and verify citations.              | It is not unrestricted model knowledge or a guarantee of correctness.                                      |
| **Corpus registry**              | Supabase records describing source identity, rights, version, hashes, pages, chunks, and ingestion state.                       | Source bytes live in private object storage, not Git by default.                                           |
| **Canonical old source**         | Old repository `origin/main` at the exact audited commit in the source manifest.                                                | The dirty/stale local checkout and unmerged branches are not canonical.                                    |
| **Parity**                       | New behavior meets an explicit product and safety acceptance contract, with current tests/evidence.                             | Similar appearance or copied files alone are not parity.                                                   |
