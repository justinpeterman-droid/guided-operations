# Data Model

**Status:** Target logical model with a locked local migration chain, private
operational record history, and retention/legal-hold foundations

## Schema boundaries

| Schema      | Exposure                               | Purpose                                                                                  |
| ----------- | -------------------------------------- | ---------------------------------------------------------------------------------------- |
| auth        | Supabase managed                       | Auth users, identities, sessions, factors                                                |
| app_private | Not exposed                            | Product records, sensitive helpers, account mapping, jobs, audit, and retrieval metadata |
| api         | Exposed but initially empty and locked | Later reviewed RPCs/views with explicit execute/select grants                            |
| storage     | Supabase managed                       | Bucket/object metadata protected by explicit policies                                    |
| pgmq        | Extension managed                      | Queue messages; never directly available to browsers                                     |

Do not place product tables in the default exposed public schema. Revoke default
anon/authenticated privileges and grant only reviewed operations. Functions are
security invoker by default. A security-definer function must live outside the
exposed schema, fix search_path to empty, schema-qualify every reference, verify
the caller, and receive an explicit execute grant through a narrow wrapper.

## Modeling conventions

- UUID primary keys generated by PostgreSQL.
- timestamptz for all instants; date/time fields remain separate only when the
  domain form distinguishes them.
- text plus check constraints for small evolvable state sets.
- snake_case identifiers.
- created_at and updated_at controlled by database defaults/triggers.
- Foreign keys have deliberate delete behavior and supporting indexes.
- JSONB is reserved for reviewed flexible structures; fields used for
  authorization, joins, retention, status, or common filtering remain typed
  columns.
- JSONB query operators receive the matching GIN or expression index.
- Cursor pagination uses a stable compound key such as (updated_at, id).
- Append-only tables reject UPDATE and DELETE through both privileges and
  triggers.
- All migrations are forward-only and immutable after shared-environment use.

## Identity and authorization

### app_private.staff_members

One row per staff identity:

- id and single facility reference
- employee_lookup_hash, a unique keyed digest of normalized input
- employee_number_hint, a bounded non-sensitive display suffix
- display_name and active/inactive status
- created_at and updated_at

### app_private.user_accounts

One row per Supabase Auth user linked one-to-one with a staff member:

- auth_user_id, primary-key reference to auth.users with restricted deletion
- staff_member_id, unique reference
- sign_in_alias, a private random Auth alias chosen by ADR-0003
- role: officer or administrator
- status: pending, active, locked, or disabled
- must_change_passcode
- failed_attempts and locked_until
- auth_version
- created_at and updated_at

The lookup hash supports login without storing an indexed plaintext employee
number. The exact alias storage/encryption design is part of the required auth
spike. Neither lookup digest nor internal alias is returned by general account
APIs.

### app_private.admin_step_ups

- id, account_id, auth_version
- purpose
- token_digest
- issued_at, expires_at, consumed_at
- request_id

Rows are session/account-bound, short-lived, purpose-bound, and single-use.

### app_private.login_rate_limits

- dimension: account, device, network, global
- subject_digest
- window_started_at, count, blocked_until

Subject values are keyed digests. Cleanup is bounded and must not race login
updates.

### app_private.account_security_events

Append-only content-free events for login, refresh/revocation, credential
change/reset, lock, role/status change, and bootstrap. Store stable IDs, action,
result, reason code, request ID, and timestamps—not employee number, secret,
alias, IP address, or user-agent text. If network correlation is required, store
a rotated keyed digest with an approved retention.

## Incident and report records

### app_private.incidents

Current-head metadata:

- id, created_by_account_id
- incident_number and display name where fictional/approved
- status
- incident date/time, facility-local context, category/classification
- current_revision_number
- created_at, updated_at, archived_at

### app_private.incident_revisions

Immutable snapshot:

- id, incident_id, revision_number
- editor_account_id, created_at, reason
- reviewed field notes/facts, gap answers, charges, validation, warnings
- schema_version
- provenance JSONB with bounded, validated keys

Unique (incident_id, revision_number). A trigger rejects update/delete. Schema
version two confirmed facts contain a bounded, unique `reportingStaffMemberIds`
array. Every ID must match a `reporting_officer` relationship on that same
revision. An empty array keeps a confirmed fact in the incident record but makes
it unavailable to report generation. Immutable schema version one rows remain
readable, but their unscoped facts cannot be used for a new draft.

### app_private.incident_staff_relationships

- incident_revision_id
- staff_member_id
- relationship: reporting_officer, preparer, involved_officer, witness
- selected_by_account_id
- created_at

Relationships are immutable and revision-bound. One through twenty reporting
officers and exactly one preparer are required at creation. The preparer is
always the authenticated actor; the browser cannot assign preparation to another
account. Every selected person must have an active account and active staff row
in the same facility. Reporting and preparing relationships grant record access;
involved and witness labels preserve attribution without silently granting
access.

The protected Report Assistant workspace is a derived read, not another durable
record. It combines the current incident revision with only the active selected
reporting officers needed to choose an attributed draft. The read omits raw
field notes, full employee numbers, account IDs, facility fields, and unrelated
staff. Draft creation then revalidates the selected officer and every selected
fact against these immutable relationships inside the server and database.

### app_private.reports

- id, incident_id, report_type
- reporting_account_id, prepared_by_account_id
- status, current_revision_number
- created_at, updated_at, archived_at

### app_private.report_access

- report_id, account_id
- relationship: owner, preparer, explicit collaborator
- granted_by_account_id, created_at, revoked_at

Unique active relationship per report/account. This table supports explicit
future collaboration without broadening facility tenancy.

### app_private.report_draft_candidates

Each immutable review-only candidate records its incident and source revision,
selected `reporting_staff_member_id`, requesting/preparing account, controlled
report type, confirmed fact IDs, cited paragraphs, and provider key. The
selected staff member must be an active `reporting_officer` on the exact source
revision, and every source fact must name that selected staff member in its
revision-local officer scope. Reporter identity is deliberately removed before
AI-provider input. Finalization derives the reporting account from this stored
selection and keeps the preparer and final revision editor as separate
attributions.

Both `app_private.reports` and immutable review-only draft candidates accept
only `first_person`, `supervisor_summary`, `cover_letter`, or `disciplinary`.
Migration application fails rather than silently coercing an older unsupported
type. The application repeats this closed-set validation at every public and
server-read boundary so malformed storage does not become trusted content.

### app_private.report_revisions

Immutable snapshot:

- id, report_id, revision_number
- editor_account_id, created_at, reason
- narrative and reviewed editable fields
- validation and warnings
- source incident revision
- source AI job where applicable
- model, prompt, template, schema, and source provenance digests/versions

Restore copies a selected snapshot into a new revision. Recovery output may be
stored as non-current history but never promoted implicitly.

### app_private.legal_holds and controlled retention deletion

- Archived incident, report, and paperwork heads expose a database-derived
  `deletion_eligible_at` exactly 730 days after the UTC archival instant.
- Archival occurs at or after the final revision. Eligibility is a review date,
  not permission to delete.
- A private legal-hold row records facility, validated scope/target, bounded
  authority reference, actor, placement time, and one immutable release
  transition.
- Facility holds protect all current record types in that facility. Incident
  holds also protect child reports. Direct incident, report, paperwork, policy,
  staff, and account scopes are validated against the facility boundary.
- The private `record_retention_status` routine classifies archived operational
  heads without deleting data. Data API roles have no direct table or function
  access.
- The server-only legal-hold adapter derives the administrator facility, lists a
  bounded same-facility register, and calls private placement/release routines.
  Protected routes require current administrator authority, trusted origin,
  session CSRF, and distinct one-time step-up purposes for placement and
  release.
- `record_artifacts` privately registers generated exports by source target,
  bucket/path, checksum, and size. `retention_deletion_requests` retains
  metadata-only authority, backup, manifest, transaction-binding, and completion
  evidence. Both tables force RLS and deny Data API roles.
- Backup-aware approval is non-destructive and expires after 24 hours. A
  separate execution proof plus exact record-ID confirmation is required.
  Execution supports only a complete incident package or one paperwork record;
  report-only deletion is rejected.
- An expired approval cannot execute. The next valid approval attempt atomically
  marks the expired request canceled, preserves it as evidence, and records a
  bounded cancellation audit event before issuing a replacement.
- Private routines lock and recheck the target and legal-hold scopes, bind the
  actor/backend/transaction, verify registered Storage cleanup, and delete the
  database package in one transaction. Append-only history tables reject all
  other deletion paths. Hosted rehearsal and owner acceptance remain required.

## Forms and packets

### app_private.form_templates

Template code, title, version, media type, Storage object ID/checksum, active
range, field schema, scope, and physical/digital classification.

### app_private.incident_packet_items

Incident, incident revision, template/report reference, required/optional state,
officer scope, sort order, and lifecycle state.

### app_private.form_instances

Packet item, source incident revision, template version, reviewed populated
fields, manual fields, completeness/gaps, current revision, and status.

If form edits need history, use `app_private.form_instance_revisions` with the
same append-only pattern rather than mutating historical values.

### app_private.physical_paperwork_acknowledgments

Packet item, actor, source revision, acknowledgment type, and timestamp. This is
guidance/history; it does not claim custody of physical documents.

### app_private.document_action_events

Append-only preview, print, download, or copy actions with parent IDs and
revision numbers. No document content.

## Operational paperwork

Use one canonical pair:

- `app_private.paperwork_records`
- `app_private.paperwork_revisions`

Supported kinds include count sheet, assignment roster, uniform inspection,
metal detector test, perimeter check, random search log, and detector sign-out.
Records hold kind/date/shift/current head. Revisions hold the immutable reviewed
definition and editor provenance. A partial unique index enforces the approved
daily uniqueness rule for active records.

The initial implemented kind is `count_sheet`. Its active record is unique by
facility, work date, and the approved shift code (`A`, `B`, `C`, `D`, `U`, or
`F`). The record stores no mutable form values. Each revision snapshots the
reviewed structure, user-entered payload, server-calculated reconciliation, and
safe provenance; revision inserts advance the current head serially. Direct
table access is denied, so later server APIs must enforce the shift-shared
relationship before invoking a purpose-specific mutation.

Archived paperwork heads use the same 730-day deletion-review clock and
legal-hold override as incident/report records.

The former duplicate operational_paperwork tables are not a second target
domain. Import reconciliation is described below and in
[legacy-migration.md](legacy-migration.md).

## Jobs, idempotency, and exports

### app_private.idempotency_records

Actor, action, idempotency-key digest, canonical request digest, response
reference/status, created_at, and expires_at. Never persist a raw credential or
secret response in a replay record.

### app_private.ai_jobs

- id, type, state, stage
- requested_by_account_id
- incident/report/document target IDs
- expected base revision/version
- provider/model/prompt/retrieval configuration versions
- attempt count, available_at
- claim token digest, claimed_by, lease_expires_at
- result references and safe result/error codes
- created_at, started_at, completed_at

The row stores control metadata and references, not large prompts/answers/files.

### app_private.task_outbox

- id, topic/job type, aggregate ID
- payload schema version and ID-only payload
- created_at, available_at, dispatched_at, attempt count, last safe error code

The domain mutation/job row and outbox row commit together.

### app_private.exports

Actor, source record/revision, format, template version, Storage object ID,
checksum, byte size, media type, created_at, expires_at/lifecycle state. Bytes
remain in private Storage.

## Policy corpus and retrieval

### app_private.policy_documents

Stable logical source: id, source code/title, owner/issuer, classification,
source type, active version ID, created_at, archived_at.

### app_private.policy_document_versions

- document ID, version label, effective date, exact source SHA-256, private
  Storage path, media type, byte size, page count, and restricted original
  filename metadata;
- rights status/evidence/reviewer/review window, allowed processing regions, and
  explicit external-AI permission;
- lifecycle and reviewed-current state, with at most one current version per
  logical document.

### app_private.policy_ingestion_runs

The immutable run identity records the source hash, environment, extraction/OCR
tool and configuration hashes, normalization/chunking versions, optional
embedding profile, code/lock hashes, counts, failures, status, and QA reviewer.
A run cannot become `ready` unless its approved page/chunk counts match the
stored evidence and it has no recorded failures.

### app_private.policy_pages

Version and ingestion-run IDs, 1-based source page index, printed label,
normalized bounded text and checksum, extraction mode/confidence, dimensions,
rotation, structured-layout reference, warnings, and QA state. Page evidence for
a ready run cannot be silently changed or deleted.

### app_private.policy_chunks

- version/ingestion-run/page range/printed labels/section path
- deterministic chunk ordinal and text checksum
- bounded chunk text
- tsvector generated/search column
- bounded character/token/overlap metadata
- lifecycle and QA state

Every new chunk must map to a contiguous stored page range of at most ten pages.
Embeddings remain in `policy_chunk_embeddings`, separate from canonical chunk
text, and identify their provider/model/dimension through an immutable embedding
profile.

Indexes:

- GIN on full-text vector;
- HNSW or IVFFlat vector index selected from measured corpus/query behavior;
- unique source/version/chunk checksum;
- B-tree on active version, document, page, and stable citation keys.

The foundation stores an untyped `vector` plus a versioned embedding profile. A
trigger requires each vector to match its profile dimensions, and profile
identity (provider, model, and dimensions) is immutable. Each activated profile
gets its own dimension-cast partial ANN index after the model is selected.
Changing models creates a parallel profile/re-embedding and activation switch;
it never reinterprets existing vectors in place.

### app_private.retrieval_evaluations

Fictional/public-safe question set, expected source/version/citation IDs,
configuration version, scores, run timestamp, and release gate. Do not store
restricted corpus passages in Git fixtures.

## Audit

### app_private.audit_events

Append-only:

- id, occurred_at
- actor account/auth IDs where available
- action, result, target type/ID
- request/correlation ID
- safe detail JSON constrained by an action-specific allowlist

Allowed details include IDs, revision numbers, action codes, counts, field-path
names, model/config versions, latency buckets, and SHA-256 digests. Reject
credentials, employee numbers, names, policy/record text, prompts, answers,
provider bodies, IP addresses, and arbitrary nested JSON.

## Authorization shape

- User read/write policies require an active account and an ownership, preparer,
  or explicit access relationship.
- Administrator policies require an active current admin row, not merely a
  possibly stale JWT role claim.
- Audit/security events are insert-through-reviewed-functions and read by
  elevated administrators only.
- Corpus reads are authenticated; corpus activation/ingest is admin plus
  purpose-bound step-up.
- Jobs are visible only to the requester/authorized record users or admins.
- Worker operations use dedicated narrow functions and do not impersonate a
  browser user.

See [auth-rbac-rls.md](auth-rbac-rls.md) for the full matrix.

## Legacy paperwork reconciliation

The former migration chain created both paperwork_records/paperwork_revisions
and operational_paperwork/operational_paperwork_revisions. Never edit or squash
an applied old migration to hide that state.

If importing a legacy database:

1. Inventory both pairs, constraints, counts, IDs, timestamps, foreign keys, and
   row-level canonical content hashes.
2. Produce a read-only conflict report; stop on non-equivalent overlapping IDs
   or unexplainable orphan rows.
3. Create a new additive migration that creates the target canonical tables if
   absent and copies only reconciled rows with deterministic provenance.
4. Validate counts, hashes, unique constraints, head/revision continuity, and
   parent references in the same release gate.
5. Switch application reads/writes to the canonical tables.
6. Leave legacy tables read-only for an observation/rollback window.
7. Remove or archive them only in a later, separately approved forward migration
   after backup and reconciliation evidence.

If there is no legacy production data, create only the canonical target tables
and retain the reconciliation decision in documentation.
